# Decisions

Newest at the bottom. Each entry: what, why.

## Step 1: Scaffold
- **UI framework: React 19.** Biggest ecosystem for canvas, markdown and drag tooling, and the most predictable to write without a live preview loop; performance for ~500 cards is handled with memoised card components and CSS transforms.
- **Package manager: npm.** Ships with Node, no extra install on the user's machine.
- **Bundle targets: NSIS + MSI only** (Windows first), instead of "all", so `tauri build` does not try other platforms.
- **Window: 1440x900 default, min 960x600**, matching the reference layout.
- **Removed `tauri-plugin-opener`** from the template; re-add it in the web-clip step if needed.
- **Build environment note:** steps were authored in a Linux workspace without a shell on the Windows machine. Rust was verified with `cargo check` and the UI with `vite build` there; `cargo tauri dev` / `build` on Windows are unverified by me (see docs/testing.md).

## Step 2: Shell + theme system
- **Layout:** the canvas fills the whole window; the sidebar (224px) and chat (340px) float over it as frosted-glass panels with a 16px margin. The floating pills center themselves in the free column between the panels via CSS. Minimum window width raised to 1100px so the title pill, zoom pill and toolbar never collide.
- **Fonts:** `@fontsource/playfair-display` (500/600, normal + italic) and `@fontsource/nunito` (400/600/700), latin subset only, imported in `main.tsx`. Vite bundles the woff2 files into the app: no CDN at runtime.
- **Shader:** the approved GLSL is used verbatim (`src/theme/shader.ts`). Time = `33 + accumulated(dt * speed)` so changing speed never makes the animation jump. Renders at `scale` (0.16) of the window and the browser upscales it. Pauses when the document is hidden, renders a single still frame under `prefers-reduced-motion`, and falls back to the flat theme color (body background) if WebGL or the shader fails or the context is lost.
- **Theme switch cross-fade:** shader palette and params are interpolated over 600ms in JS; UI colors transition via CSS (0.5s). The saved theme is applied before first render (`bootTheme`) so there is no flash of the default colors.
- **Theme data:** types match the schema in the brief. `ui.glass` is a number (alpha 0..1). Stage dot colors are theme-specific; derived values (glows, soft tints) are computed in `applyTheme`.
- **Non-Pearl presets:** shader palettes are exactly as specified; UI tokens were tuned by me to keep text contrast >= 4.5:1. `npm run check:themes` prints every checked pair. Gold sky uses slightly lower sheen (0.14) and Iridescent higher iridescence (0.5).
- **Contrast checks** (`src/theme/contrast.ts`) test text against the worst-case surface: the theme's fallback color under the glass alpha, and a 30% white "cloud card".
- **Persistence for now:** selected theme id in `localStorage`. Replaced by `workspace.json` in step 3.
- **Demo cards and disabled chat controls** on the canvas/chat are placeholders to judge the look; real cards arrive in step 4 and chat in step 6.
- **Sidebar Theme switcher** is a row of four 44px swatches above "New project".

## Step 3: Storage core
- **Where the logic lives:** `src-tauri/src/storage.rs` (pure Rust, no Tauri types, fully unit-tested), `model.rs` (serde types = the JSON contract with the UI), `watcher.rs`, `state.rs` (workspace root + watcher lifecycle), `commands.rs` (thin Tauri wrappers). Commands are `#[tauri::command(async)]` so file IO never runs on the UI thread.
- **Workspace location:** `%USERPROFILE%\Dreamer` by default. The chosen root is remembered in the app config dir (`config.json`), not inside the workspace. `DREAMER_WORKSPACE` env var overrides it for dev/tests. `set_workspace_root` exists; a settings UI for it comes later.
- **Card id = file name.** The `id:` in frontmatter is ignored on read and rewritten from the file name, so copying a card file can never create duplicate ids. IDs are ULIDs; ids and project slugs are validated (`[a-z0-9_-]`, no dots or slashes) so no command can reach outside the workspace.
- **Links live in card frontmatter (`links[]`), not in `canvas.json`.** `canvas.json` holds `viewport` and per-card `{x, y}`. One source of truth per fact, and git diffs of a card show its links. (The brief listed links under both; this resolves it.)
- **Unknown frontmatter keys are preserved** on rewrite (`extra`), so hand edits and notes Claude adds are never lost. Unknown `stage`/`source` values fall back to `cloud`/`user`. CRLF and BOM are accepted on read; files are always written with LF.
- **Body normalisation:** leading/trailing blank lines are trimmed; files end with exactly one newline. This keeps in-memory and on-disk text identical (a test caught a mismatch here).
- **Lenient loading:** an unreadable card file becomes a warning on the project (shown as a small pill), never a failure. A corrupt `workspace.json` or `canvas.json` is copied to `*.json.bak` and defaults are used, so one bad edit cannot stop the app from starting.
- **Reconcile on load:** cards created outside the app (Claude Code, git) get a free grid position and it is saved; positions of cards deleted outside the app are dropped.
- **Delete is always move-to-Trash** (`trash/<id>.md` + `trash/trash.json` with reason label, old position). `restore_card` puts it back at its old position; `empty_trash` is the only permanent delete and the UI must confirm it. `trash_card(reason)` is already there for step 7's "lost to <winner>". Variant folders move with the card.
- **Atomic writes:** temp file in the same folder, fsync, rename over the target; temp names end in `.tmp` and are ignored by the watcher.
- **Watcher:** `notify` + debouncer (250ms) on the workspace root, recursive. Emits `workspace-changed` with de-duplicated `{scope, project}` events; the UI reloads the affected project. `.git` and temp files are ignored. The app's own writes also trigger a reload (harmless, idempotent).
- **YAML crate:** `serde_yaml 0.9` (marked unmaintained upstream but stable and exactly what is needed). Swap later if it becomes a problem; the format is plain YAML.
- **Theme choice** now lives in `workspace.json` (localStorage is only a first-paint cache) and follows external edits to that file.
- **UI data layer:** `src/api` exposes one typed `Api`; inside Tauri it calls the Rust commands, in a plain browser (`npm run dev` without Tauri) it uses an in-memory mock so the look can be developed and screenshotted without the Rust core.
- **Temporary UI in step 3:** the toolbar "Card" button creates a Cloud card titled "New idea" so storage can be exercised; ghost cards' Keep/Dismiss already work (Keep clears `ghost`, Dismiss moves to Trash). Real editing, drag and pan/zoom are step 4.

## Step 4: Canvas
- **Camera math:** `viewport = {x, y, zoom}` is the CSS translate+scale of `.world`; pan/zoom update it directly (wheel = pan, Ctrl/⌘+wheel = zoom at the cursor). A native (non-passive) `wheel` listener is used instead of React's `onWheel`, because React 17+ makes its own wheel listener passive and `preventDefault()` inside a passive listener is a no-op (would leak into page/browser zoom otherwise).
- **Persistence is optimistic + debounced:** dragging a card or panning updates `data.canvas` in React state immediately (`patchCanvas`) and schedules `save_canvas` 400ms later (`scheduleCanvasSave`); mouse-up on a drag flushes immediately. The app's own write re-triggers the file watcher, which reconciles into the same state, so there's no visible jump.
- **Images and web clips reuse `fields`, not new frontmatter keys.** `fields.image` holds a `media/<ulid>.<ext>` path (written by the new `save_media` Rust command, read back as a base64 data URL by `read_media` — simplest thing that works without an asset-protocol capability). `fields.url` / `fields.clip_title` hold a web clip's link and title. This avoids a model/schema change for a step-4 feature; the three keys are excluded from the generic custom-fields editor in `CardEditor` and rendered specially.
- **Card body markdown** is rendered by a hand-rolled ~40-line renderer (`src/util/markdown.ts`): headings, bold/italic, links, lists. Deliberately not a full CommonMark implementation — avoids a new dependency for what is card notes, not documents.
- **Links stay directional and label-light.** A link is created by toggling the toolbar's Link tool and clicking two cards (source, then target); it's stored as before, in the source card's `links[]`. Labels are edited by clicking into the label field in the card editor's Links section, not on the canvas itself (keeps the SVG overlay — `LinkLayer` — purely a renderer, no hit-testing).
- **Undo/redo is a linear stack of `{undo, redo}` closures** built in `useWorkspace`, pushed by `createCard`/`updateCard`/`deleteCard`/`moveCard`. Create's inverse is delete+restore (not re-creating with the same content), so a card's id is stable across an undo/redo cycle — links pointing at it don't break. Ctrl+Z/Ctrl+Shift+Z/Ctrl+Y are global `keydown` listeners that bail out while an `<input>`/`<textarea>` has focus, so native text-field undo still works inside the card editor.
- **Keeping 500 cards smooth:** `CardView` is `React.memo`'d and the world only renders cards whose bounding box intersects the viewport (plus a 400px margin) — `onScreen` in `CanvasArea`. Positions are read straight from `canvas.cards` (a plain object), so there's no per-card subscription overhead.
- **Quick capture window:** built lazily (`show_capture_window` in `lib.rs`) rather than declared in `tauri.conf.json`, so it doesn't appear at startup. It loads the same `index.html` with `?capture=1` and `App.tsx` branches into a tiny `CaptureWindow` component before anything else (theme provider + shader background only, no workspace hook) — keeps the popup instant and independent of the main window's state. It calls `create_card` directly via `invoke`, hard-coded to the `inbox` slug (quick capture always lands in the Inbox per the brief).
- **Global hotkey** is registered from Rust (`AppState::register_hotkey`, using `tauri-plugin-global-shortcut`'s `AppHandle` extension trait) at startup and again whenever `update_settings` is called with a new `hotkey`. No capability entry was needed for this because it's a direct Rust→plugin call, not a webview→native IPC call (capabilities gate the latter). The `capture` window *does* need a capability entry (added to `windows` in `capabilities/default.json`) because it calls `invoke` from JS.
- **Minimize-to-tray:** the main window's `CloseRequested` event is intercepted (`prevent_close` + `hide`) in `lib.rs`'s `setup`; only the tray menu's "Quit" actually exits. The tray menu also offers "Show Dreamer" and "Catch a thought" (opens the capture popup without the hotkey).
- **Verified for real on Windows this session** (a real shell was available): `npm install`, `cargo test` (18 tests), `npm run check:themes`, `npm run build`, and `npm run tauri dev` — confirmed the real command round trip (workspace files appear under a throwaway `DREAMER_WORKSPACE`), and the live file watcher (a card written from PowerShell outside the app was picked up and reconciled into `canvas.json` automatically). Global-shortcut registration produced no error in the dev log. Not independently re-verified: `fs::rename` over a file an external program is holding open (antivirus/editor) — the existing atomic-write design (temp file + rename onto the target) sidesteps the common case, but a lock on the *target* path itself during a delete/trash rename is still a plausible Windows-only failure mode; see docs/testing.md.

## Step 5: Claude sidecar + chat panel
- **The sidecar (`sidecar/claude-sidecar.mjs`) is a thin, protocol-only bridge, not a second copy of the storage logic.** It uses `@anthropic-ai/claude-agent-sdk`'s streaming-input `query()` (one long-lived session per app run, fed by an async queue so many chat turns share one process and one Claude Code session) with `tools: []` (every built-in tool off) plus a single custom MCP server (`createSdkMcpServer`) exposing exactly two tools: `create_card` and `ask_question`. `create_card` does not touch the filesystem itself — it sends a `tool_request` line over stdout and awaits a `tool_response` on stdin, so every card still goes through the one real writer, `storage::Workspace`, with the same atomic writes, ULIDs and ghost/ghost-source defaults as everywhere else (`source: claude`, `ghost: true`, enforced in Rust, not trusted from the model). There is no delete tool, matching "Claude never deletes."
- **No API key, by construction.** The sidecar never touches `ANTHROPIC_API_KEY`; the Agent SDK shells out to the user's own `claude` CLI, which carries whatever login Claude Code already has (`~/.claude/.credentials.json` on this machine). `permissionMode: "bypassPermissions"` is safe here specifically because `tools: []` already removed every built-in (Bash, Edit, Write, ...) — the only thing left to auto-approve is the one MCP server we wrote ourselves.
- **Session continuity needs no plumbing.** Because one Node process keeps one `query()` generator alive for the whole app session, "resume" is just "the process is still running" — the frontend never sends or stores a session id. Restarting the app starts a fresh Claude Code session (acceptable for a first pass; `resume`-across-restarts would mean persisting the SDK's session id into `workspace.json`, left for later).
- **Card context travels as a plain formatted string, not structured JSON**, built in `ChatPanel.formatContext` and handed to Rust as the `context` argument of `claude_send`, which just prepends it to the user's text before forwarding to the sidecar. The sidecar's prompt-handling code therefore never needs to know Dreamer's card schema at all — only Rust and the chat panel do.
- **`/grill-me` answers are recorded by the host, not trusted to the model.** `ask_question` returns immediately (it only *shows* the question, via a `question` stdout event); when the user clicks a choice, `ChatPanel` both appends "Q/A" to the selected card's body through the normal `updateCard` path (so it's undoable and saved exactly like any other edit) and sends the choice back as the next chat turn, in that order — the card is updated whether or not the model's next reply ever arrives.
- **The "is Claude set up" check is deliberately shallow:** `claude_status` just runs `claude --version`. There's no cheap, side-effect-free way to check login status without starting a real session, so a logged-out CLI is instead caught the first time the user actually sends a message (the SDK's `authentication_failed` error surfaces as a normal chat error bubble). The setup screen covers "Claude Code isn't installed"; "installed but logged out" is a one-line error in the chat, not a second screen.
- **Packaging gap, flagged for step 9:** `tauri.conf.json` bundles `sidecar/claude-sidecar.mjs` as a resource, but not its dependencies — `@anthropic-ai/claude-agent-sdk` and `zod` live in the repo's top-level `node_modules/`, which is not bundled. In dev, Node's normal upward module resolution finds them because the sidecar is spawned with its cwd set two levels up (the repo root). A packaged installer needs either a bundled `node_modules` alongside the sidecar resource or a bundled Node runtime; neither is done yet. Until then, `cargo tauri build` produces an app whose chat panel will fail to start the sidecar unless it happens to run from a dev checkout.
- **Verified for real this session:** `sidecar/claude-sidecar.mjs` was run standalone against the real, already-logged-in Claude Code install (not mocked) — confirmed streaming text deltas, a full `create_card` tool round trip (including the `tool_request`/`tool_response` handshake a test harness stood in for Rust), and a real `ask_question` call with model-generated multiple-choice options, across two separate conversations. `cargo check`/`cargo test` (18 tests, unchanged) and `npm run build` are clean with the new Rust (`sidecar.rs`) and TypeScript (`api/claude*.ts`, `state/useClaudeChat.ts`, the rewritten `ChatPanel`) in place, and `npm run tauri dev` starts and runs without error with the sidecar module compiled in. Not driven live: clicking through the chat panel inside the actual WebView2 window — there is no GUI automation tool for the native window available this session (only Chrome-based browser automation, and the app's `__TAURI_INTERNALS__` bridge only exists inside the real window, so pointing a browser at the Vite dev URL falls back to the mock API instead of exercising the real IPC path). See docs/testing.md.

## Step 6: Branch, compare, trash
- **A fork is a loose tag, not a new data structure.** `Card.branch` (already reserved as `Option<Value>` since step 3) holds `{"group": "<id>", "of": "<origin card id>"}`; any cards sharing the same `group` are siblings in one fork set. This needed one small Rust change — `NewCard` gained a `branch` field so `create_card` can set it (it was previously hardcoded to `None`) — and nothing else in storage; `branch` was already preserved on read/write via the normal frontmatter round trip.
- **"Give me 3 takes" assigns the branch group by instructing the model, not by post-processing its output.** `ChatPanel` generates a `crypto.randomUUID()` client-side and rewrites that one chip's message into an explicit instruction naming the exact `branch_group`/`variant_of` values to pass to `create_card` on all three calls (the sidecar's `create_card` tool schema grew those two optional fields to allow it). This was sanity-checked twice against the real model (see docs/testing.md) and it reliably copied the id verbatim across all three tool calls both times. If a model ever failed to do so, the three cards would simply not group — no crash, just a missed "compare" affordance — so the risk of trusting model instruction-following here is low.
- **"Pick winner" reuses `trash_card`'s existing reason label**, now reachable from the UI via a new `lose_card` command (a thin wrapper Rust already had the logic for since step 3, just never exposed). Losing siblings get reason `lost to "<winner title>"`; the winner's own `branch` field is deliberately left as-is rather than cleared — harmless (an unresolved compare with one card left just shows "no other forks to compare"), and avoids adding a `branch` field to `CardPatch` for a cosmetic cleanup.
- **The diff in "compare view with diff" is a real (if small) diff**, not just side-by-side text: `util/diff.ts` is a ~30-line LCS line-diff, run between each sibling's body and the first-created sibling's body (the implicit baseline), with additions/deletions highlighted inline in `BranchCompare`.
- **Trash view reading:** "two-way restore choice" is read here as *restoring is always on the table* (contrasted with Empty Trash, which is the one irreversible, confirm-gated action) — not a per-item choice between two destinations. `TrashView` lists every trashed card for the active project with its reason and a Restore button, plus a confirm-first "Empty trash" for the whole list.
- **Verified for real this session:** the model's instruction-following for `branch_group` was re-tested end to end against the real Claude Code install with the exact wording `ChatPanel` sends — it set the same group id on all three `create_card` calls in a fresh conversation. `cargo test` (18, unchanged), `cargo check`, `npm run build`, and `npm run check:themes` are all clean with the branch/compare/trash code in place. The compare view's diff, the fork badge, and the Trash view's restore/empty flow were not driven through the live window this session (same native-window GUI-automation gap noted for steps 4-5); they're built directly on `ws.loseCard`/`api.restoreCard`/`api.emptyTrash`, which were each exercised live in step 3/4's testing. See docs/testing.md.

## Step 7: Theme editor + brief export
- **Custom themes are plain JSON files Rust never interprets.** `storage::list_custom_themes`/`save_custom_theme`/`delete_custom_theme` read/write `themes/<id>.json` as opaque `serde_json::Value` — the shape (`Theme` in `src/theme/types.ts`) is validated only on the TypeScript side (`isTheme` in `ThemeContext`), the same trust split as cards' `fields`. A custom theme's `id` goes through the same `check_slug` used for project slugs, so it can't escape the workspace folder.
- **Live preview reaches the shader, not just CSS.** `ThemeContext` gained a `setPreviewTheme(theme | null)` that, while set, replaces the resolved theme app-wide — `ShaderBackground` already re-renders whenever `theme` changes, so `ThemeEditor`'s sliders/color pickers preview instantly with no extra plumbing. The preview is pure UI state; nothing is written to disk until Save.
- **Per-project theme override uses the field that was already there.** `ProjectMeta.theme` (`Option<String>`, settable since step 3 via `update_project`) just needed a resolver: `ThemeContext` takes a `projectTheme` prop (passed from `App.tsx` as `ws.data?.meta.theme`) that wins over the global default when set. The picker lives in the canvas title pill, not Sidebar, since it's specific to the open project; the Inbox has no override (it's shared context, not a "project" in the pitch-deck sense).
- **Brief export is enforced in Rust, not just a disabled button.** `storage::export_brief` re-checks `card.meta.stage == Stage::Pitch` and returns the same "unlocks when the card reaches Pitch" error the UI shows, so the lock holds even if something else calls the command directly. It writes a self-contained Markdown file to `briefs/<id>.md` (title, tags, body, linked-card ids/labels, custom fields) — the existing `briefs/` folder, created but unused since step 3, finally has a writer. Export auto-saves the editor's pending edits first (so "set stage to Pitch, then immediately Export" works in one flow) but does not close the editor, matching Save's separate "also closes" behavior.
- **Verified for real this session:** `cargo test` — now 20 (two added: a custom-theme round trip that also confirms a corrupt sibling file is skipped rather than failing the list, and a brief-export test proving the Pitch lock and checking the written Markdown's content). `cargo check`, `npm run build`, `npm run check:themes` clean. `npm run tauri dev` run live again: dropped a hand-written `themes/test-theme.json` into a throwaway workspace while the app was running, confirming no crash (the watcher's "themes" scope classification itself was already covered by a Rust test). Not driven live: the Theme editor's sliders/pickers, the per-project theme picker popover, and the Export brief button clicked inside the actual window — same native-window GUI-automation gap as prior steps. See docs/testing.md.

## Step 8: Polish
- **Found and fixed a real undo gap while doing this pass:** dragging a card was never pushing an undo entry. `moveCard`'s old code tried to read "the previous position" from `dataRef` at drag-end, but by then every intermediate `onPointerMove` had already written through to that same state, so the "previous" position it read was just the drag's current (already-moved-to) position - undoing a drag would have been a no-op. Fixed by having the drag handler in `CanvasArea` pass the drag-start position explicitly (`{ undoable: true, from: {x: d.ox, y: d.oy} }`) instead of asking `moveCard` to infer it. This is the kind of bug that's invisible until you actually trace "what does Ctrl+Z do after each action" end to end, which is what this step was for.
- **Esc closes the top-most modal**, added as one small shared hook (`useEscClose`) rather than five copies of the same `useEffect`. Also added: Esc cancels an in-progress Link-mode pick (previously only a background click did).
- **A third empty state**: "No cards in this filter" when the stage filter hides every card on an otherwise non-empty canvas (previously just a blank canvas with no explanation).
- **The capture popup now shows its own errors** instead of silently failing - it calls `create_card` directly via `invoke` (no `ws.run()` wrapper, since it's a separate window with no workspace hook), so it needed its own try/catch.
- **500-card performance was checked by argument, not a live profiler**, because there is no GUI-automation tool available for either the native WebView2 window or (this session) a connected Chrome browser extension. The case for 60fps at 500 cards: `CanvasArea`'s pan/zoom path only ever mutates `canvas.viewport`, never `canvas.cards`, so `CardView`'s `pos`/`card` props keep the same object references during a pure pan - React.memo skips re-rendering all 500 card components, and only the `.world` CSS transform changes (GPU-accelerated). A drag similarly only replaces the one dragged card's position in `canvas.cards` (`{...c.cards, [id]: pos}` keeps every other key's reference), so only that one `CardView` re-renders per pointer-move. The `visible`/`onScreen` `useMemo`s do re-run every pan tick (their only dependency, `data`, changes because `patchCanvas` always returns a new top-level object even when `cards` itself didn't change) - but that's one `Array.filter` over <=500 items, microseconds, not a 60fps risk. A `?stress=1` flag was added to the mock API (`npm run dev`, browser-only) that seeds a 500-card project for anyone who wants to eyeball this directly; it's dev-only and adds nothing to the production bundle's behavior.
- **Reduced motion and error handling** were mostly already in place from earlier steps (the global `prefers-reduced-motion` rule from step 2 covers every animation added since, since none of steps 4-7 added a new `@keyframes`; `ws.error` toasts and the chat panel's inline error bubbles already covered the main mutation paths). This step's audit didn't find further gaps beyond the two above.

## Step 9: Build and final docs
- **`cargo tauri build` works and was verified for real this session**, including installing and running the result (a real shell was available, so this didn't have to wait for the user): both NSIS and MSI bundles build cleanly in release mode; the NSIS installer was run silently (`/S /D=<dir>`) into a throwaway directory, the installed `dreamer.exe` was launched directly (not `tauri dev`), created a fresh workspace on first run exactly like the dev builds, and picked up a file written from PowerShell outside the app via the live watcher - the same round trip verified in steps 4-7, now confirmed against the actual packaged binary. The uninstaller was then run silently and removed the install directory cleanly.
- **Tried, and deliberately reverted, bundling the sidecar's `node_modules` into the installer.** `sidecar/package.json` now declares its two real dependencies (`@anthropic-ai/claude-agent-sdk`, `zod`) for documentation and so `npm install --prefix sidecar` works if someone wants a self-contained sidecar folder, but `node_modules` itself is not committed or bundled: `npm install --prefix sidecar` produced ~8,000 files / ~384MB, and bundling that into the NSIS installer made `makensis` hang long enough that it looked stuck (killing it produced a bundler failure, confirming it was still working, just extremely slow on that many small files). Given a packaged build still needs a system `node` on PATH regardless (Tauri does not bundle a JS runtime), paying that bundle-size and build-time cost for only *half* the dependency problem solved wasn't worth it. The installer therefore ships the same thin `sidecar/claude-sidecar.mjs` resource as before; running the chat panel from an installed build still additionally requires Node.js on the machine with `@anthropic-ai/claude-agent-sdk` reachable (e.g. installed globally, or the repo's `node_modules` present) - this is the same gap flagged in step 5, now confirmed (not just reasoned about) to be the right scope to leave for a later packaging pass rather than a quick fix.
- **Bundle size for context:** `Dreamer_0.1.0_x64-setup.exe` is ~2.0 MiB, the MSI ~2.8 MiB - both installers, not just the exe. This is the whole point of the plain-file/no-database/no-bundled-runtime design holding up: the app itself stays tiny; only the optional Claude integration has an external runtime dependency.

## Setup: in-app Claude sign-in
- **Two setup states instead of one.** The chat panel's setup screen (`ClaudeSetup.tsx`) now separates "Claude Code not installed" (offers **Install Claude Code**) from "installed but not signed in" (offers **Sign in with Claude**). It shows whenever `installed` is false or `loggedIn` is explicitly `false`; if the login state can't be determined (`null`, e.g. an old CLI without `auth status`), the chat is allowed to try rather than being blocked on a parsing problem.
- **Login status comes from `claude auth status --json`** (checked with `claude --help` / `claude auth --help` on CLI 2.1.322). It prints `{"loggedIn": bool, "authMethod": ...}`; `parse_auth_status` reads that, with a plain-text fallback. The previous step-5 note ("no cheap, side-effect-free way to ask") is obsolete.
- **Sign-in runs `claude auth login`**, Claude Code's own browser OAuth flow (Claude subscription by default), as a child process. Dreamer never sees a password, token, or API key; there is no API-key path anywhere. While it runs, the panel shows "Waiting for browser sign-in..." with Cancel. If the CLI prints a sign-in URL, the panel offers "Open the sign-in page" as a fallback, which goes through `claude_open_login_url` and only accepts `https://` URLs on `claude.ai` / `claude.com` / `anthropic.com` (and their subdomains), so that command can't launch arbitrary URLs. stdin is kept open (piped, never written) for the job's lifetime, because some CLIs treat a closed stdin as "user aborted".
- **Install runs `npm install -g @anthropic-ai/claude-code` from Rust**, with stdout and stderr streamed line by line (ANSI codes stripped) to the panel as `claude-setup` events, and a status re-check when it finishes. Only one setup job runs at a time. Cancel kills the whole process tree (`taskkill /T /F` on Windows), because `npm.cmd` / `claude.cmd` run under `cmd.exe` and killing only the direct child would leave Node running.
- **Executable resolution doesn't trust PATH alone** (`claude_setup::candidate_paths`). A GUI-launched app may not inherit the terminal's PATH, so after PATH it checks `%USERPROFILE%\.local\bin\claude.exe` (native installer), then `%APPDATA%\npm\claude.cmd` (npm global). On Windows only `.exe` / `.cmd` are considered, since `Command` can't run the `.ps1` or the extensionless shell shim npm also writes. The found path is shown in the panel; when nothing is found, the error lists every place that was searched. `npm` and `node` resolve the same way (PATH, then `%ProgramFiles%\nodejs`), and children get the resolved tools' folders prepended to PATH, so `claude.cmd` (which calls `node`) works from a short GUI PATH. The sidecar's `node` now goes through the same resolver.
- **Native installer before npm shim** in the fallback order (PATH still wins over both). Observed on the dev machine: two installs side by side (npm 2.1.322 on PATH, an older native 2.1.196 in `.local\bin`). With a full PATH the npm one is used; with a GUI-short PATH the native one is. Both share the same `~/.claude` credentials, so either works for status and sign-in, and the panel shows which one it found.
- **No console windows:** every child Dreamer spawns (`claude`, `npm`, `taskkill`, the sidecar's `node`) uses `CREATE_NO_WINDOW` on Windows, so release builds (GUI subsystem) don't flash a black console for each status poll.
- **No restart needed.** While the setup screen is visible and no job is running, it re-polls `claude_status` every 4 seconds, so a sign-in done in a separate terminal is picked up too. The backend remembers the last "ready" state (installed and not signed out); when it flips to ready, or when an in-app `claude auth login` exits successfully, the running Node sidecar is shut down. The next chat message starts a fresh one, which reads the new credential. Status polling is skipped while npm is installing so it doesn't probe a half-written CLI.
- **Failure messages in plain words** (`describe_failure`): network errors (`ENOTFOUND`, `EAI_AGAIN`, `ECONNREFUSED`, `ETIMEDOUT`, `fetch failed`, ...) → "Couldn't reach the internet..."; npm `EACCES` / `EPERM` → a permission explanation; Node version (engine) errors → "update Node.js"; login cancel / timeout wording; npm not found → "Install Node.js from nodejs.org (it includes npm)". Anything else shows "Install/Sign-in didn't finish: <last output line>".
- **Instructions text fixed:** the manual terminal fallback is now a numbered list with each command in its own block (install, then `claude auth login`) inside a "Prefer a terminal?" disclosure, instead of two bare commands that could run together.

## Retrieval: card search tools
- **Plain files plus an in-memory index; no database and no embeddings.** `search.rs` keeps, per project, a map from card id to a pre-tokenized document, plus the card file's `(mtime, size)` stamp. A search over 500 cards scores every document in memory (about 0.2 ms warm in release and about 1.3 ms in a debug build; see docs/testing.md).
- **Incremental updates ride on the existing watcher instead of a new one.** The watcher callback in `state.rs` now marks the affected project dirty in the index before it emits `workspace-changed`. The next search re-stats that project's `cards/*.md` and re-parses only files whose stamp changed or that are new, and it drops files that disappeared. The watcher's events are per project rather than per file, so the stamp diff is what keeps this incremental (a test asserts that exactly one file is re-parsed after one edit). A project nobody has searched yet is indexed lazily on first use. Switching the workspace root throws the index away. The sidecar's `create_card` marks its project dirty directly, so a search straight after creating a ghost card doesn't wait for the 250 ms watcher debounce.
- **Trash comes for free:** trashing moves a card's file from `cards/` to `trash/`, and only `cards/` is indexed. Ghost cards are indexed and carry `ghost: true` in results, and the Ctrl+K list and chat chips show them as suggestions.
- **Scoring:** for each query term, title 10, tags 6, fields 4, body 1. Body hits use diminishing returns (`1 + ln(count)`), and a term that is only a prefix of a card word (3+ characters) counts half. The total is then scaled by `0.4 + 0.6 * coverage^2` (coverage is the share of query words matched), so a card matching every word beats one that repeats a single word. A multi-word query that appears verbatim in a title gets a title-weight bonus.
- **Normalization and stemming:** text is folded with NFKD plus combining-mark removal (new dependency: `unicode-normalization`) and a few special letters (ß, æ, œ, ø, đ, ł). Stemming strips `ing`, `ed`, `es` (after s/x/z/ch/sh), `s` (not `ss`/`us`/`is`), and `ies`/`ied` → `y`. It undoubles a consonant that `ing`/`ed` left behind (running → run, but falling → fall), and drops a trailing `e`, so game, games, gaming and gamed all meet. Words under 4 letters and words containing digits are left alone. The `image` field (a media path) isn't indexed.
- **Snippet:** about 200 characters, starting about 50 characters before the densest cluster of matches, with whitespace collapsed and `…` at cut ends. It comes from the body if any query word hits the body, otherwise from the joined field values.
- **Claude's retrieval tools are read-only by construction.** `search_cards`, `read_card` and `list_related` are answered by `sidecar::run_tool` from the index and never call a storage write. `read_card` looks in the open project first, then anywhere (ULIDs are unique across projects), and resolves the linked cards' titles. `list_related` returns links in both directions (same project), then cards sharing tags (any project), strongest first, each with its reason. `search_cards` defaults to all projects, and Claude can pass `scope: "project"`. The new system prompt says: "Before answering questions about the user's ideas, search the cards. Cite cards by title. Never invent cards." There is still no delete or edit tool, and `create_card` still forces `ghost: true`.
- **`/related` uses a fourth tool, `propose_link`, which proposes but never writes.** Rust validates it (both cards exist in the open project, the cards are different, and the link doesn't already exist) so Claude gets a real error instead of a false "done". The sidecar then emits a `link_proposal` event. The UI holds proposals in memory (`useWorkspace.ghostLinks`) and draws them as dashed accent lines with a Keep/Dismiss pill at the midpoint (the reason shows on hover). Keep writes a real link through `update_card`. Undoing a Keep removes the link and brings the proposal back; undoing a Dismiss restores it.
- **Trade-off: proposals aren't persisted**, so they disappear if Dreamer restarts before you act on them. Writing them to a card file would make them "real" links, which the brief rules out, and a separate proposals file felt like more machinery than v1 needs. Re-running `/related` recreates them.
- **The "Suggest links" chip became `/related`.** The old chip only asked for links in prose; `/related` produces the same suggestions as actionable ghost links. It's disabled (with a tooltip) until a card is open, since it's about one card.
- **Chat shows Claude's searches.** Every `search_cards` call emits a `search` event attached to the reply being written, which renders as "Searched cards: <query>" plus one chip per result. Results from another project show that project's name, and ghost results get a dashed outline.
- **Clicking a result chip** calls `ws.focusCard(id, project)`, which switches project if needed, selects the card (it becomes the chat's context card and gets an accent ring), and pans and zooms to it. The pan is centered in the free column between the sidebar and the chat panel, with a 0.45 s eased camera move (instant under reduced motion), at zoom `max(current, 1.15)`. If the card's stage is filtered out, that stage is turned back on. A result that was trashed in the meantime shows an error toast instead of moving the camera.
- **Ctrl+K calls the same `search_cards` command, with no Claude call.** It searches all projects by default, with a This project / All toggle. Typing is debounced 100 ms, and out-of-order responses are dropped. Arrow keys plus Enter work, and Esc closes it. The shortcut works even while typing in a field, because Ctrl+K has no text-editing meaning in Dreamer.

## Fix pass 1: Scrolling (issues #2, #6)
- **One system, two pieces, in `src/ui/Scroll.tsx`.** `ScrollArea` renders every scrollable region: the chat thread, the setup log, every dialog body, the trash list, the Ctrl+K results, the fork-compare columns, the project-theme popover, the sidebar's project list (new; it used to just overflow), and the markdown preview. Textareas get the same `.scroll scroll-y` class. A wheel boundary marks the root of a panel or popup (`boundary` on a ScrollArea, `useWheelBoundary(ref)`, or `data-wheel-boundary` on a static element such as a canvas pill). A shared `Modal` (`src/ui/Modal.tsx`) now wraps every dialog, so they all get the boundary, the scroll area and Esc handling the same way.
- **Look:** the scrollbar is a 10px themed bar from Chromium's classic `::-webkit-scrollbar` (WebView2 is Chromium). The thumb is the theme's ink at 58% and the track is ink at 7%, both set by `applyTheme`. `scrollbar-width` and `scrollbar-color` are deliberately not set anywhere, because in Chromium 121+ they switch back to native, auto-hiding bars.
- **"Always visible" and "no layout shift":** the gutter is reserved up front (`scrollbar-gutter: stable`), so content never reflows when the bar appears. The bar shows whenever the content is longer than the area, and never fades out like an overlay bar. Areas whose content fits show no thumb in the reserved gutter; painting an empty track on every short dialog read as broken. The one-off rules (`overflow: auto` on `.chat-body`, `.modal`, `.trash-list`, `.palette-results`, `.setup-log`, `.theme-picker-pop`, `.compare-columns`) are gone.
- **Wheel routing:** the canvas's native wheel listener now returns early when the event starts inside any wheel boundary (pills, the toolbar, ghost-link controls, the theme popover, any dialog backdrop, including the parts inside `<main>` such as the card editor and trash). It also returns early when the event starts inside a `.scroll` area that can still scroll in the wheel's direction, which is how long card bodies (section 2) scroll. Everything else pans, or zooms with Ctrl. Boundaries also stop propagation natively, because React's `stopPropagation` runs at the root, which is too late for the canvas's native listener.
- **Cards count as canvas, not popups.** Wheeling over a card whose body can't scroll further pans the canvas. Requiring the cursor to be over empty canvas would make panning a dense board nearly impossible. Ctrl+wheel always zooms, even over a card body.
- **Chaining:** nested scroll areas use `overscroll-behavior: auto`, so the browser's own chaining passes leftover scroll from an inner list to the dialog body around it. Boundary areas use `contain`, so chaining stops at the panel. Chat, sidebar and the dialogs are sibling panels, never nested, so scroll can't cross between them.
- **Contrast:** `check:themes` now also checks the scrollbar thumb against its track on glass, at 3:1 (WCAG 1.4.11, non-text UI). Its first run failed on all four built-in themes at a 50% thumb (2.66 to 2.84), so the alpha was raised to 58% (3.24 to 3.49).
- **Esc now closes only the top-most dialog** (`useEscClose` keeps a stack). Before, Esc in Compare forks also closed the card editor underneath it, and the canvas's link-mode Esc stands down while a dialog is open.

## Fix pass 2: Cards (issues #7, #8, #9)
- **Size and stacking live in `canvas.json`, next to the position.** `Pos` gained optional `w`, `h`, `z` and a `back` flag, all omitted from the file when unset, so old canvases load unchanged and stay diff-friendly. `Canvas::sanitize()` runs on every read and save: it resets non-finite coordinates, clamps sizes to 160×90 up to 4000, and turns a non-finite size back into "auto". The minimums are mirrored in `src/components/cardGeometry.ts`. New cards, including Claude's ghosts, get `z = max + 1`, so they land on top. Trash stores the whole `Pos`, so restoring a card brings back its size and stacking too.
- **Auto height vs. manual size:** absent `h` means auto. The card grows with its content, and the body (now rendered markdown, 15px, no 4-line clamp) grows up to about 18 lines, then scrolls inside the card with the shared scroll system. The first manual resize writes both `w` and `h`, measured from the real rendered box, and from then on the card keeps that size. "Stop auto-growing once resized" is therefore just "`h` is present". Resizing never moves neighbouring cards, and overlap is allowed.
- **Handles:** each corner has a 44×44 handle centred on it (the touch-target rule). Edges have 14px strips between the corners. Making the edge strips 44px thick would swallow most of a small card's title and body for dragging, and the corners already give a full-size target for every resize direction. Handles show on hover and on the selected card. Dragging the top or left handles moves `x`/`y` so the opposite edge stays put (`resizeRect`).
- **Stacking:** pressing on a card (to drag or open it) raises it to the front, which covers both "last clicked" and "last edited", since editing starts with a click. The ⋯ button on each card (44px) and right-click both open a menu: Open, Bring to front, Send to back. Send to back sets `back: true`. A card that is completely covered by a card above it is lifted to the front for display only (`displayStack`). It is never persisted and never applied to a card the user sent to the back. That check is O(n²) over the cards on screen after culling, not all 500.
- **Undo:** resize, Bring to front and Send to back push entries that restore the card's whole canvas entry. Raising a card that is already on top is a no-op with no entry, so plain clicks on the top card don't flood the stack.
- **Fixed a real bug on the way: canvas undo didn't stick.** `flushCanvas` saved `dataRef`, which only caught up after the next render, so "patch, then flush" wrote the previous canvas. `undo()` also reloaded from disk without waiting for the save, so an undone drag could snap back. Canvas patches now update `dataRef` synchronously, `flushCanvas` returns its promise, and undo entries await it. `moveCard` also used to replace the whole `Pos`, which would have wiped size and z on every drag; it now merges.
- **Performance at 500 cards:** `CardView` was wrapped in `memo` but received the whole `ws` object, which is new on every render, so every card re-rendered on every drag or pan frame. It now gets stable callbacks (`cardActions`, a ref-backed `onOpen`) plus primitives, so only the card that changed re-renders. Rendered heights come from one `ResizeObserver` per card on screen, batched into a single re-render per animation frame. They feed culling, link endpoints, fit-to-view and focus, which now all use real card sizes instead of the fixed 236×150.
- **Editor:** it's now the large dialog size. The notes textarea and preview take most of it (at least 42vh, 16px). Custom fields and Web clip URL sit behind a "+ More" toggle, collapsed by default. When a card has values there, the toggle shows a count, and its open/closed state is remembered per card in `localStorage` (a per-viewer UI convenience, not card data). Each section has a one-line helper text.
- **Security fix:** card bodies now render markdown on the canvas, so `renderMarkdown` now escapes `"` and `'`. Before, a crafted link such as `[x](https://a/"onmouseover="…)` in any card file could inject attributes into the `href`. This was verified with a one-off script: the string now renders as inert text.
- **Contrast:** `check:themes` now also checks muted text on cards (the menu button, the resize grip, helper text) and accent on cards (links in card bodies). All four themes pass.

## Fix pass 3: Housekeeping (issues #1, #3, #4)
- **Theme dialog:** it now uses the same `Modal` (large size) as the card editor and compare view. It's a two-column layout: controls on the left (colour pickers enlarged to 44px, sliders in 44px rows), and a sticky live preview on the right. The preview renders the draft through the same CSS variables the app uses. `themeVars(t)` was factored out of `applyTheme`, so a container can scope a theme to itself. It shows a glass panel with ink, body and muted text, an accent button and a chip, the four stage cards, a ghost card, a link, and either the contrast warnings or an all-clear line. The whole app behind the dialog still previews the draft as before. Under 900px the two columns stack.
- **Delete project goes to the Recycle Bin.** It uses the `trash` crate (v5), which on Windows uses the shell's recycle operation, so the user can restore the folder from Explorer. If recycling fails (for example a network drive or no recycle bin), the folder is deleted outright, the error is logged, and the toast says "deleted from disk" rather than "moved to the Recycle Bin". The confirmation dialog shows the exact folder path, says the files leave the disk, and says that this can't be undone inside Dreamer. That's why it isn't in the undo stack: the stack is per project and empties when you switch projects, and the project is gone. Restoring from the Recycle Bin is the way back, and the watcher picks a restored folder up live.
- **Guards:** the Inbox is refused, both in Rust and by the UI having no button for it. An unknown slug is NotFound. Rust also refuses any folder that isn't exactly `<root>/projects/<slug>`. `last_project` is cleared if it pointed at the deleted project. The UI moves the selection to the Inbox before deleting, so the follow-up reload never asks for a missing project. The watcher already reported the deleted folder as a "project" change, and the search index drops projects that no longer exist on its next full refresh. There is no Claude tool for this, and the sidecar has no path to it.
- **Chat threads:** there's one thread per card, keyed by card id, and a "project" thread when no card is selected. Each is a plain JSON file at `<project>/chats/<thread>.json` holding `{version, sessionId, messages}`, written atomically. Rust stores it as opaque JSON, the same trust split as custom themes. Thread names are validated like card ids, so they can't escape the folder. The file watcher now ignores `<project>/chats/`, because the chat panel writes those on every turn and reloading the canvas for each write would be churn.
- **One Claude session per thread in the sidecar,** keyed `<project>/<thread>`. A thread resumes its saved `sessionId` (Agent SDK `resume`), so conversations survive restarts. At most 3 sessions are live at once, since each is a Claude Code process; the least recently used idle one is closed and simply resumed when needed. A saved session that no longer exists (the SDK reports a zero-turn error result, then throws) is replaced by a fresh session, and the waiting message is replayed instead of failing. Each session gets its own MCP server instance, because an SDK server object binds to one transport.
- **Reset chat** (in the chat header, behind a confirmation) clears only the current thread. It deletes that thread's file through Rust, sends `reset_thread` to the sidecar to close that session, and drops the saved session id, so the next message starts fresh. This is a user-initiated deletion of chat history only; Claude still can't delete anything.
- The chat header's "Clear" button was 30px tall, which broke the 44px rule; it's now a normal 44px chip next to Reset chat.
- **Contrast:** the new "Delete project" button is a fixed (not themed) dark red, so `check:themes` now has a row for white on that red (7.18:1).

## Fix pass 4: Claude chat (issues #5, #10, #11)
- **Project context on every turn, built in Rust.** `sidecar::send_message` prepends `search::format_project_context`, built from the in-memory card index (no extra disk scan). It holds the project name, the card count, and one line per card (`title [tags] · stage`, with `*` marking unkept ghost suggestions), most recently updated first. The order matters because the cap keeps the freshest cards. It is capped at 200 cards and 12,000 characters, whichever comes first, with at most 6 tags and 90-character titles. Anything cut off ends with "…and N more cards not listed." The UI adds only the selected card's details (title, id, stage, tags, notes) under `[Selected card]`; the old "Other cards: up to 24 titles" line is gone because Rust's overview covers it. Claude can call `read_card` for full card text and links.
- **Retrieval was left alone in this pass.** The brief puts RAG and search tools out of scope here because a separate retrieval prompt exists. That prompt has already been implemented (commit "Retrieval: card search tools": `search_cards`, `read_card`, `list_related`, `propose_link`). This pass keeps those tools exactly as they were and only rewrites the tone and grilling instructions around them.
- **Input:** the message box is a textarea that grows with its text up to half the chat panel's height, then scrolls inside (shared `.scroll` styling). Enter sends, Shift+Enter adds a newline, and Enter during IME composition never sends. The height is recomputed on every text change, so clearing after send shrinks it back to one line.
- **Tone:** the system prompt now asks for formal, neutral and concise replies, with no exclamation marks, flattery, filler or emoji. It replaces "chatty, encouraging collaborator". The UI's own copy was neutralised to match ("Project chat", plus a plain empty-state line per thread).
- **/grill-me structure:** an explicit 8-item checklist (`GRILL_ITEMS` in the sidecar): core experience, target player, core loop, key mechanics, setting and tone, scope and platform, what makes it different, biggest risk. Items the notes already answer are skipped. Each turn is exactly one `ask_question` call and nothing else: no preamble, no reaction to the previous answer, no praise. After the last item, Claude calls `create_card` once to propose a ghost spec card (title `Spec: <card>`, stage draft, tag `spec`, linked to the card as "spec of", one section per item built from the answers and notes), and the only chat text is "Proposed a spec card." Answers still go straight into the card's notes when clicked, as before, and that edit is undoable.
- **The duplicate question is fixed at both ends.** `question` events now carry `turnId`, and the UI attaches the question to that reply, which then renders only as the question card. A grill turn (the `/grill-me` chip, or any answer click) is marked `quiet`, so while it streams it shows "…" instead of text. The live test showed the model still adds "The next question is on the card above." after asking, and once even wrote a made-up "[Answer] …" itself. So the sidecar now drops all text for a turn once `ask_question` has fired, and the tool's result tells the model to end its turn and not guess an answer.
